# Mobile app architecture

Draft, 14 November 2026 ([#50](https://github.com/gardner/weedz/issues/50)).
This describes the app we intend to build. So far only the scaffold in
[`mobile/`](../mobile) and its pure-Dart domain layer exist: the report model
and the approval rules.

The app scans the phone's photo library **on the phone**, finds photos that
probably show a watchlist weed, and prepares a report for each one. The person
looks at every report and approves or declines it. **Only approved reports leave
the phone.** A report carries the exact location where the photo was taken,
with its accuracy, because exact locations are what make a report useful for
science. The approval screen therefore always shows that exact location before
the person agrees to share it.

## Decision: Flutter

The project lead chose **Flutter**: one Dart codebase for Android and iOS.
Native code is limited to the places a platform needs it, and the main one is
model inference (see below). Flutter is pinned at 3.50.0 (Dart 3.14) in CI. The
org id `org.example` is a placeholder until the project has a domain to publish
under ([#62](https://github.com/gardner/weedz/issues/62)).

Other options considered, briefly:

- **Native apps per platform** (Swift and Kotlin). This gives the best access to
  each platform's ML stack, but every screen and rule is written and tested
  twice.
- **React Native** or **Kotlin/Compose Multiplatform.** Both are viable. Flutter
  was chosen.
- **Screening on the server** (uploading photos to be scanned there). This
  removes the model-size problem, but it would send whole private libraries off
  the phone, which defeats the privacy design.

## Module layout

```text
mobile/
  lib/
    domain/        pure Dart, no plugins: the report (#57 schema v1), approval
                   states, scoring and window geometry. Unit tested on any machine.
    scan/          photo-library access, the scan queue and its local index (#53)
    inference/     the Dart side of the image encoder (a Pigeon interface)
    location/      capture time and location, with accuracy, per photo (#54)
    reports/       building reports from scan results, and the approval screens (#56)
    upload/        the intake client, secure token storage, retries (#57)
    models/        downloading and verifying model artefacts (#59)
    main.dart
  pigeons/         Pigeon definitions for typed platform channels
  ios/Runner/      Swift: the Core ML image encoder, and PhotoKit where photo_manager stops
  android/app/     Kotlin: the LiteRT image encoder
  test/            unit and widget tests; test/fixtures holds contract fixtures
```

Dependencies point inwards. `domain/` imports nothing beyond `package:meta`, and
the feature folders depend on `domain/`, never on each other's internals.

## Inference runtime

Only BioCLIP 2's **image tower** runs on the phone. The prompts are fixed, so
the server computes their text embeddings once and ships them as a table of 16
vectors ([#51](https://github.com/gardner/weedz/issues/51),
[#52](https://github.com/gardner/weedz/issues/52)). Scoring an image against
that table, and the revision 4 ranking, is small and lives in Dart in `domain/`.

[#52](https://github.com/gardner/weedz/issues/52) measured on a desktop which
compressed image towers still agree with the reference
([pilot results](pilot-nelson-tasman.md)):

- **fp16 (608 MB) keeps parity.** Every margin moved by less than 0.0006.
- **ONNX dynamic int8 (306 MB) fails.** Two native lookalikes newly pass as
  weeds.
- The smaller BioCLIP ViT-B/16 tower is a different model and fails too.

So **the starting point is the fp16 BioCLIP 2 image tower**, run where phones
are fast at fp16: the Neural Engine and GPU.

**Choice: each platform's own runtime, behind one Pigeon interface.**

| Platform | Runtime | Model artefact | Accelerator |
| --- | --- | --- | --- |
| iOS | Core ML, called from Swift | ML Program (`.mlpackage`) converted with coremltools, fp16 | Neural Engine, then GPU (`computeUnits = .all`) |
| Android | LiteRT CompiledModel API, called from Kotlin | `.tflite` converted with litert-torch, fp16 | GPU, with CPU (XNNPACK) as fallback |

The Dart side sees a single interface, roughly
`Future<List<Float32List>> encodeWindows(List<WindowPixels>)`, generated by
[Pigeon](https://pub.dev/packages/pigeon) so both sides are typed. Each
platform implements it in about a hundred lines of native code. We call the
vendor runtimes directly rather than through a community Flutter plugin,
because:

- `tflite_flutter` is no longer maintained, and its successor
  [`flutter_litert`](https://pub.dev/packages/flutter_litert) is a
  single-maintainer community package;
- the Flutter ONNX Runtime and ExecuTorch packages are community-maintained,
  and do not expose every accelerator option we need to measure;
- Android's NNAPI is deprecated from Android 15, so a plugin that leans on it
  is a dead end.

**Fallback: ONNX Runtime Mobile** (the official Objective-C and Android
packages, behind the same Pigeon interface), with the CoreML execution provider
on iOS and XNNPACK on Android. #52 showed that ONNX export alone is exact. If a
Core ML or LiteRT conversion cannot pass parity, this route reuses the already
measured ONNX graph, at a likely cost in Android speed.

### The parity gate is a hard requirement

**No model artefact ships to a phone unless it passes the #52 parity gate,
measured on a real phone.** This applies to every artefact: each converted
model, each runtime or accelerator setting, and each later "optimisation".

- The gate is `weedz.discovery.parity` (thresholds version 1) and
  `scripts/compare_optimised.py`, run on the 30 pilot and 39 lookalike photos.
  The window embeddings come from the device runtime, and they are scored
  against the server's text table.
- It checks the whole path, not just the network: decoding, letterboxing and
  tiling, resizing and normalisation all run on the phone. Resampling filters
  differ between platforms, so the app's pre-processing is part of what is
  measured. The window geometry is ported to `domain/`, with fixtures generated
  from `weedz.discovery.inference`.
- It runs on at least one recent iPhone (Neural Engine) and one mid-range
  Android phone (GPU). An accelerator can drift from desktop fp16, so a pass on
  one device class does not cover another.
- The model registry (#59) records which artefact passed, on which devices,
  under which thresholds version. The app refuses an artefact whose hash is not
  in that record.
- The measurements that #51 deferred are taken at the same time: size, peak
  memory, seconds per photo, battery drain and heat. They are reported, not
  gated, until we set phone budgets.

A model of about 600 MB is not bundled in the app. It is downloaded after
install, on Wi-Fi by default, then hash-checked (#59). The text table and the
model revision travel with it, and each report records the model it came from
(`model.model_key`, `revision`, `ranking_revision`, `score_meaning`).

## Photo-library scanning flow

Scanning is detailed in [#53](https://github.com/gardner/weedz/issues/53). The
shape is:

1. **Permission.** The app asks for photo access with
   [`photo_manager`](https://pub.dev/packages/photo_manager).
   - On iOS the person can grant only a limited selection. The app scans that
     selection, says plainly that it covers only part of the library, and
     offers the system picker to change it.
   - On Android 14 and later, partial access (`READ_MEDIA_VISUAL_USER_SELECTED`)
     is treated the same way.
   - Google Play allows `READ_MEDIA_IMAGES` only when photo access is an app's
     core function, which a library scanner is. It needs a declaration (#62).
2. **Index.** A local SQLite index ([drift](https://pub.dev/packages/drift))
   records each asset's id, modification time and the model revision that
   scanned it, plus the best margin per weed. A restart resumes where it left
   off, a new model revision re-scans, and a photo is never scanned twice by
   the same model.
3. **Queue.** Newest photos are scanned first, a few windows at a time. The
   queue backs off when the phone is hot or the battery is low.
   - iCloud-only (iOS) or cloud-only (Android) originals are skipped by default
     and counted, so the app can say how many were not scanned.
4. **Background.** Scanning mostly happens while the app is open, with
   progress shown. Longer scans use what each platform allows:
   - iOS: `BGProcessingTask` while charging, and on iOS 26 a
     `BGContinuedProcessingTask` that the person starts and can see.
   - Android: WorkManager, or a `mediaProcessing` foreground service, which
     Android 15 limits to 6 hours a day.
   - Scanning never uploads anything (see Privacy).
5. **Candidates.** A photo becomes a report candidate when it passes the same
   ranking rule as the server (revision 4). The crop is the window that won.

## Location and time

Location and time are detailed in [#54](https://github.com/gardner/weedz/issues/54).
The app reads the capture time and the camera's GPS position from the photo:

- on iOS, from `PHAsset.location`, a `CLLocation` with `horizontalAccuracy`;
- on Android, from EXIF, which needs `ACCESS_MEDIA_LOCATION`; without it, the
  system redacts the GPS tags.

Accuracy comes from the platform or from EXIF `GPSHPositioningError`. Coordinates
are kept at full precision.

**A location without a known accuracy is not sent as if it were exact.** The
server requires an accuracy with every location. When a photo has none, the
report has no location unless the person supplies one, and this is shown to
them. Whether to allow a stated default accuracy instead is left to #54.

## Report approval flow

The approval flow is detailed in [#56](https://github.com/gardner/weedz/issues/56).
The rules are already code in `mobile/lib/domain/approval.dart`:

```text
found ─► pending ──approve──► approved ──send──► sending ──receipt──► received ──► withdrawn
            │  ▲                 │               │  ▲
            │  └──── any edit ───┘     no answer │  │ send again: same id, same content
            │                                    ▼  │
            │                                 unanswered ──► withdrawn
            │
            │      sending ──413/415/422──► refused ──revise──► revised (final)
            │                                                   + a new pending case, new id
            └──decline──► declined (final; also from approved and refused)
```

- **One report, one decision.** There is no "approve all". Each report is
  approved on its own screen.
- **The approval screen shows exactly what will be sent:**
  - the crop, if the person chooses to include it;
  - the suggested weed, worded as a suggestion to be checked, not an
    identification (lookalikes exist; see the pilot results);
  - the capture time;
  - the exact location, on a map with its accuracy circle, and as coordinates
    in numbers;
  - the consent wording and the licence they choose for the crop.
- **The person can remove details before approving.** "Remove location" and
  "Don't send the photo" both change the report, so it needs approving again.
  An approved report cannot change silently. Any edit returns it to pending,
  and in the domain model an `Upload` comes only from `startSending()`. That
  call freezes an approved `ReportCase` and returns its body as JSON text, all
  in one step.
- **Once sent, a report is frozen.** After a send with no answer, the server
  may already have the report, so its id must keep meaning that content. The
  report can only be sent again unchanged, or withdrawn.
- **The store commits each transition by id, compare-and-set.** A
  `ReportCase` is an immutable value, so an old copy (for example, the
  approved case after `startSending()`) can still be called. The store
  therefore saves a transition only if the stored case still has the status
  it started from. It saves `startSending()`'s frozen case before
  dispatching its `Upload`, and `revise()`'s retired and new cases in one
  transaction. The uploader sends an `Upload` only while the stored case for
  its id is `sending`.
- **Declining is final** for that report. Declined photos are remembered so
  they are not suggested again under the same model.
- **After sending**, the receipt is kept. The person can withdraw the report
  from the same screen (`DELETE`), which deletes the crop on the server.

Accessibility (VoiceOver, TalkBack, dynamic type, large tap targets for
Approve and Decline) is part of this flow, not an add-on
([#63](https://github.com/gardner/weedz/issues/63)).

## Upload contract

The app speaks version 1 of the intake contract from
[#57](https://github.com/gardner/weedz/issues/57) (`src/weedz/intake/`). It is
JSON over HTTPS, and nothing about it is Flutter-specific.

- **Send:** `PUT /reports/{report_id}`
  - The id is a random lower-case UUID that the device chooses when the report
    is found, and it is kept across retries. A retry with the same content gets
    the same receipt, never a duplicate.
  - Headers: `Authorization: Bearer weedzsub_<id>_<secret>` and
    `Content-Type: application/json`.
- **Body:** the `Report` model in `mobile/lib/domain/report.dart`. Absent
  optional fields are left out.
  - The body is at most 2,000,000 bytes, and the crop at most 1,000,000 bytes
    and 4096 × 4096 pixels.
  - The crop is JPEG, PNG or WebP. The app re-encodes it from pixels, so no
    EXIF, XMP or GPS travels in it, even though the server strips metadata
    too. The domain `Crop` type checks the format, the byte limit and strict
    padded base64. The crop's pixel size comes from the screening window that
    produced it.
  - `test/fixtures/report_v1.json` is the contract fixture. The Dart test checks
    the model against it, and `tests/test_mobile_contract.py` validates it with
    the server's Pydantic `Report`.
- **Answers:**

  | Status | Meaning | What the app does |
  | --- | --- | --- |
  | 201, 200 | Receipt: `report_id`, `status`, `received_at`, `withdrawn_at`, `image` | Mark the report received |
  | 401 | The token is missing or revoked | Stop sending and ask the person to re-enrol |
  | 409 | This id was used for different content | Cannot happen, since a sent report is frozen. Treat it as refused and report the bug |
  | 410 | Withdrawn | Mark the report withdrawn |
  | 413, 415, 422 | Refused as too big or malformed | Mark it refused and show why. It is never sent again under that id. The person can decline it, or revise it into a new case with a new id |
  | 429 | Over the daily budget | Retry after `Retry-After` |
  | Network error, 5xx | No answer | Mark it unanswered: frozen, since the server may have it. Retry with backoff under the same id, or withdraw |

- **Receipt:** `GET /reports/{id}`. **Withdraw:** `DELETE /reports/{id}`.
- **Token storage:** the submitter token lives in
  [`flutter_secure_storage`](https://pub.dev/packages/flutter_secure_storage)
  (the iOS Keychain, with *after first unlock, this device only* so background
  retries can read it; the Android Keystore). It is never logged, and never put
  in a URL. Operators issue and revoke tokens with
  `uv run main.py intake add|list|revoke`.

## Privacy properties

These are the properties the design has to keep. #55 owns the full privacy
design. #61 settled that locations are shared exactly by default, never
generalised, and that a point obscured by its source stays obscured.

1. **Nothing leaves the phone without approval of that specific report.** The
   app never uploads photos, the scan index, embeddings or locations. The only
   things it sends are approved reports, and requests to fetch receipts or
   withdraw. The type system enforces the first part: an `Upload` exists only
   for an approved `ReportCase`, frozen in the same step.
2. **What is shown is what is sent.** The approval screen renders the report
   that will be serialised, including its exact coordinates and accuracy. Any
   change needs approving again.
3. **Minimal reports.** A report has no free text beyond an optional credit
   name. The crop is optional, needs its own consent and licence, and carries
   no metadata.
4. **No third-party tracking.** There is no analytics or advertising SDK. Any
   crash reporting must exclude photos, locations and tokens. The app talks to
   two hosts only: the intake server and the model download host.
5. **Local data stays local and can be removed.** Uninstalling the app deletes
   the index and unsent reports. Withdrawing a sent report deletes its crop on
   the server.

## Open questions

- **Phone budgets.** How much size, memory, time per photo and battery is
  acceptable? This is measured with the parity gate (#51) and needed before
  release.
- **Will an fp16 ViT-L fit on mid-range Android?** Peak memory on the desktop was
  1.1 GB. If it does not fit, the fallbacks are gentler int8 schemes or fewer
  windows, and each one is a ranking change that needs its own validation.
- **Ranking without the original-subject comparison.** A phone photo has no
  source taxon, so the revision 4 ranking changes on the phone. That needs its
  own check before reports are trusted (#52 noted this).
- **Enrolment.** How a phone gets its submitter token, for example by scanning
  a QR code from an operator during the pilot, and how a token is revoked if a
  phone is lost.
- **Locations without accuracy.** Should the app leave the location out, or
  use a stated default (#54)?
- **Explicit location consent** ([#91](https://github.com/gardner/weedz/issues/91)).
  The report is to gain `consent.location`, true exactly when a location is
  sent, mirroring `consent.image`. When the server accepts it, the Dart
  `Consent` gains the same field, and `withoutLocation()` sets it to false.
  Until then the app keeps to the current version-1 schema, which refuses
  unknown fields.
- **Contributor-chosen protection** (a follow-up from #61). Should a person be
  able to mark one report as obscured on the phone, for example a photo taken
  at home? It would be opt-in per report, not a default.
- **Cloud-only photos.** Should the app download originals from iCloud or
  Google Photos to scan them? This costs data and time.
